# 実装前ゲート

Vamp Pon は、まだゲーム実装に入らない。

まず、必要な情報・設計・デザイン方針を揃える。

## 基本方針

**全ての重要情報が出切るまで、ゲーム本体は作らない。**

先に作るのは、コードではなく以下。

- コンセプト
- 体験設計
- 差別化ポイント
- 見た目の方向性
- 操作感
- 画面構成
- 敵/武器/強化の役割
- MVPで作る範囲
- 作らない範囲
- 技術選定
- フォルダ構成
- デザイン資料
- 実装順序

## なぜ先に実装しないか

ヴァンサバ系は、雑に作り始めるとすぐに「よくあるコピー」になる。

さらに個人開発では、以下で失速しやすい。

- 武器を増やしすぎる
- 敵を増やしすぎる
- アートで迷う
- UIが後回しになる
- 面白さの核が曖昧なまま実装する
- 最初のプロトタイプが何を検証しているか分からなくなる

そのため、実装前に「何を作るか」「何を作らないか」を固める。

## 実装に入ってよい条件

以下が揃うまで、ゲーム本体の実装に入らない。

### 1. コンセプト

- 一言で説明できる
- 既存ヴァンサバ系との差が言える
- 個人開発で作れる規模になっている

### 2. コアループ

- 1プレイの流れが決まっている
- 序盤/中盤/終盤の体験が分かれている
- 何が気持ちいいか分かっている
- 何で失敗するか分かっている

### 3. 前後左右中央の危険エリア

- 何を表示するか決まっている
- プレイヤー判断にどう効くか決まっている
- UIとしてどう見せるか決まっている
- 危険度の仮計算が決まっている

### 4. デザイン方向性

- 世界観
- キャラの見た目
- 敵の見た目
- UIトーン
- 色味
- 参考にする/しない作品
- 仮素材の方針

### 5. MVPスコープ

- MVPで作るもの
- MVPで作らないもの
- 完了条件
- 失敗条件

### 6. 技術方針

- 使用技術
- フォルダ構成
- 実装順序
- dev/build/typecheck の方針

### 7. 作業ルール

- このリポジトリ外を触らない
- 常にコミット・プッシュする
- 大きい作業を分割する
- 実装前にdocsへ反映する

## まだやらないこと

- Phaserセットアップ
- package.json追加
- src実装
- ゲーム本体コード
- 敵や弾の実装
- 武器実装
- レベルアップ実装
- 素材制作の作り込み

## 今やること

今やるのは企画・設計・素材準備。

優先順:

1. ゲームの方向性を絞る
2. 既存作品との差を明確にする
3. 画面構成を考える
4. UI/UXを考える
5. デザイン方向を決める
6. 敵/武器/強化を役割ベースで整理する
7. MVPに入れるものを絞る
8. 実装順序を確定する

## 実装開始の合図

実装に入るときは、明示的に以下のように宣言する。

```txt
実装開始。Phase 1: Vite + TypeScript + Phaser の最小起動を作る。
```

それまでは、コードを書くよりdocsを積む。
