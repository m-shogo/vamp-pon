# Implementation PR Review Checklist

## 目的

Vamp Pon の実装PRをレビューする時に、単なる動作確認だけでなく、MVPスコープ・スマホ体験・破綻防止を確認する。

PRレビューでは「動くか」だけでは足りない。

以下も見る。

```txt
Prototypeの目的から外れていないか
スマホ前提を守っているか
データ駆動を壊していないか
MainSceneが巨大化していないか
次のPrototypeへ進む判断材料が残るか
```

---

# 1. PR基本情報

```txt
PR:
Branch:

Related Issues:

Date:
```

# 2. スコープ確認

## Prototype 1 PRの場合

入ってよいもの。

```txt
[ ] 起動
[ ] 縦持ちキャンバス
[ ] ユイ仮表示
[ ] 移動
[ ] インクの影
[ ] 夜の鉛筆
[ ] 欠片
[ ] XP/Lv2
[ ] 簡易HUD
[ ] 被弾最小
[ ] debug最小
```

入っていたら危険。

```txt
[ ] 武器5種
[ ] パッシブ5種
[ ] 記憶カプセル
[ ] 進化
[ ] 必殺技
[ ] 本格デザイン
[ ] 図鑑
[ ] 永続強化
```

危険項目が入っている場合、理由が必要。

---

# 3. 起動/ビルド

```txt
[ ] pnpm install が通る
[ ] pnpm dev が起動する
[ ] pnpm build が通る
[ ] TypeScriptエラーがない
[ ] console errorが致命的でない
```

## 注意

Prototype初期ではテストが未整備でもよいが、純粋関数を増やしたらテストも増やす。

---

# 4. スマホ確認

```txt
[ ] スマホブラウザで表示できる
[ ] 縦持ちで画面が収まる
[ ] bodyがスクロールしない
[ ] タッチ入力が反応する
[ ] 指で自キャラが隠れすぎない
[ ] 文字が小さすぎない
```

## No-Go

```txt
PCでは動くがスマホで確認していない
```

Prototype 1からスマホ確認する。

# 6. コード構造

```txt
[ ] MainSceneに全部書きすぎていない
[ ] 入力処理が分離されている
[ ] 敵スポーン処理が分離可能
[ ] 武器処理がデータ駆動へ拡張可能
[ ] 調整値が散らばっていない
[ ] 型定義がある
```

## 危険サイン

```txt
weapon.nameで分岐している
敵IDごとのif文が増えている
数値が複数ファイルに直書きされている
UIとゲームロジックが密結合している
```

---

# 7. データ駆動

```txt
[ ] 武器定義はdataにある
[ ] 敵定義はdataにある
[ ] パッシブ定義はdataにある
[ ] ウェーブ定義はdataにある
[ ] 進化条件はdataにある
```

Prototype 1では一部未分離でもよい。

ただし、Prototype 2へ進む前に分離する。

# 8. デバッグ/検証補助

```txt
[ ] debug表示がある
[ ] 敵数が見える
[ ] 欠片数が見える
[ ] Lv/XPが見える
[ ] 経過時間が見える
[ ] debugを本番表示しない仕組みがある
```

---

# 9. アクセシビリティ

```txt
[ ] 音なしでも状態変化が分かる
[ ] 被弾が視覚的に分かる
[ ] レベルアップが視覚的に分かる
[ ] 色だけで判断させていない
[ ] 揺れ/数字などを将来OFFにできる構造
```

---

# 10. パフォーマンス

Prototype 1では軽いはずだが、今後のために確認する。

```txt
[ ] 敵が増えても極端に重くない
[ ] 欠片が増えても極端に重くない
[ ] 毎フレーム重い全探索をしすぎていない
[ ] オブジェクトプール導入の余地がある
```

---

# 11. ドキュメント更新

PR内容に応じて更新。

```txt
[ ] 仕様が変わったらGDD正本を更新
[ ] 数値を調整したらbalance-logへ記録
[ ] 素材を追加したらasset-license-logへ記録
[ ] Prototype検証したらplaytest reportを書く
```

---

# 12. レビュー判定

```txt
APPROVE / REQUEST CHANGES / HOLD
```

## APPROVE条件

```txt
Prototype目的に合っている
スマホ確認できる
重大なスコープ逸脱がない
次の検証に進める
```

## REQUEST CHANGES条件

```txt
動かない
スマホで破綻
スコープ逸脱
巨大MainScene化
データ駆動を壊している
```

## HOLD条件

```txt
実装は動くが、Prototypeの目的から外れている
判断に必要な検証ログがない
```

---

# 最重要

PRレビューは、作業量を褒める場ではない。

```txt
このPRで、次に進む判断材料が増えたか？
```

これを見る。
