- S1 use: old ledger / repair tag / family phrase as evidence seed
- status: `HIGH_VALUE_CANDIDATE / EXACT YEAR-PLACE-PEOPLE OPEN`

## Ordinary life before the incident

生活は「常に悲惨」ではない。

- 学校が再開していく
- school meal / food distributionが生活の大きな支えになる家庭もある
- 壊れた衣服 / 道具 / 家具 /灯具を直して使う
- 間借り / temporary household /親族宅での同居等がある
- fuel / food / materialの順番を待つ
- official distributionとinformal mutual aidが並存する
- 子どもは不足の全体像より「今日何を食べる / 遊ぶ / 学校へ持っていく」を先に見る

トモリのrepairは「貧しいから偉い」ではない。

> **直せる物を直すのが、本人には普通。**

## Why the system was created

物資が足りない。

地域ごとに:

- household size
- child / older person presence
- residence
- fuel need
- food allocation
- repair / housing need

の情報がばらばらだと:

- 二重受取
- 取りこぼし
- 長いqueue
- clerk workload
- unfair rumor

が増える。

そこでfictional local administration / distribution bodiesが:

> **共同配給整理簿**

を作る。

目的は悪ではない。

> 「同じ条件なら、同じように届くようにしたい。」

## Pressure escalation

復興が進み、人の移動が多い。

- 帰ってきた人
- 親族宅へ一時的にいる人
- 間借り
- 住所変更途中
- household recordの更新待ち
- 子どもだけ別世帯へ預けられているcase

等、Realityの生活がledgerより速く変わる。

当初はclerkが口頭確認で補っていた。

しかし shortage / fraud fear / complaint が増え:

> `帳簿に載っている = 配れる`
>
> `帳簿に載っていない = 今回は配れない`

へ硬化する。

## Failure sequence

```txt
1. ledger creates fairness
2. exception handling becomes slow
3. unofficial judgment is accused of favoritism
4. staff are ordered to use only recorded household data
5. “not verified” becomes “not eligible”
6. living person is treated as an empty row
```

事件名「空欄世帯」は:

> record上は世帯の欄が空いている /合わない

ことから後世についたworking label。

人間そのものを「空欄」と呼ぶ差別語にはしない。

## Why the system was created

New network use creates real fear:

- impersonation
- fraud
- malicious contact
- unauthorized account use
- suspicious sellers / recruiters
- harassment

Schools / companies / local groups independently start exchanging:

> 「このname / handle / phone / accountは注意」

information.

> **相互確認連絡網**

Goal:

> warningを早く共有して被害を減らす。

## Era-specific mechanism

This is not a modern cloud platform.

Information moves through:

```txt
mail
→ forwarded mail
→ BBS post
→ downloaded list
→ printed copy
→ fax
→ school/company local database
```

Copies proliferate.

The central problem:

> **warning travels faster than correction.**

## Failure sequence

```txt
1. a warning prevents real trouble
2. more organizations join
3. allegation / confirmed fact fields are copied inconsistently
4. one false or outdated entry spreads
5. original entry is corrected
6. copied versions remain everywhere
7. “listed somewhere” becomes proof by repetition
```

A person can then be quietly denied:

- school opportunity
- job interview
- club / rental / local participation Candidate

without one dramatic ban order.

- may know less tech than child, or far more through work
- worries about bills / stranger contact / school safety
- may support warning network because it prevented something real

### Aunt / Uncle / Non-parent Adult Lens

High-value:

- family’s first PC-savvy adult

- understands that copied list cannot simply be recalled

Possible:

- learns e-mail to receive family photo

- or distrusts it because anyone can print one

Different older people disagree.

### School staff / HR / Community organizer Lens

- wants safety
- cannot verify every report
- fears liability for ignoring a warning

This is the institutional pressure.

## Food / culture texture

## Why the system was created

Identity continuity has real stakes.

Possible fraud / dispute:

- stolen remote body
- duplicated credential
- unauthorized memory-state copy
- contract executed by wrong instance
- two persons claiming same prior account history
- Android backup restored after original continued living

A strong identity system is needed.

`単一継続認証` initially guarantees:

> one legal person -> one currently valid continuity chain

Benefits:

- contract clarity
- medical / care record continuity
- fraud reduction
- inheritance / property clarity
- civic permission
- remote-body safety

## Failure sequence

```txt
1. continuity credential prevents serious fraud
2. edge cases are manually reviewed
3. copy / body migration becomes common
4. dispute volume grows
5. system requires exactly one active “authentic” continuity
6. all branches except one lose legal access
7. “credential invalid” becomes “person invalid”
```

Affected possibilities:

- Human after body migration
- branch copy with independent new experiences
- Android restored from shared snapshot
- original body and remote instance disagreement
- legal family relationship split across continuity decisions
